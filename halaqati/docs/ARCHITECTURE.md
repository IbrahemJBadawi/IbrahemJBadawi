# البنية والقرارات

## الطبقات
- **المتصفح**: صفحات React (Server Components غالبًا)؛ JavaScript محدود في النماذج التفاعلية فقط.
- **الخادم (Next.js)**: Server Actions تتحقق من المدخلات بـ Zod، ثم تستدعي Supabase **بهوية المستخدم** (وليس بمفتاح الخدمة)، فتنطبق سياسات RLS على كل طلب.
- **قاعدة البيانات**: كل الصلاحيات تُفرض في PostgreSQL (RLS + دوال RPC من نوع SECURITY DEFINER للعمليات المركّبة والمدققة). الواجهة طبقة عرض فقط.

مفتاح الخدمة (`service_role`) لا يُستخدم إلا لتحديد معدل المحاولات قبل تسجيل الدخول، في وحدة `server-only`.

## الأدوار
| الدور | المصدر | يُضاف ذاتيًا؟ |
|---|---|---|
| طالب، ولي أمر، محفّظ | `user_roles` | نعم |
| معلّم دورات، كفيل | `user_roles` | من الإدارة حاليًا (لوحاتها في مراحل قادمة) |
| إدارة المنصة | `user_roles` | لا، أبدًا (bootstrap من SQL ثم منح من مدير) |
| أمير مركز | `center_memberships.role = admin` | يُنشأ مع المركز |
| مدير دار | `organization_memberships.role in (owner, admin)` | يُنشأ مع المؤسسة |

مبدّل الدور في الواجهة يغيّر العرض فقط. لا يمكنه منح أي صلاحية، ويُتحقق منه على الخادم مقابل الأدوار الفعلية.

## دوال الصلاحيات (schema `private`، غير مكشوف عبر API)
`has_role`، `is_platform_admin`، `is_org_admin`، `is_center_admin` (يشمل مدير الدار المالكة)، `is_halaqa_manager`، `is_halaqa_staff`، `is_halaqa_student`، `is_parent_of`، `can_view_student`، `can_view_profile`.

## نموذج البيانات (المرحلتان 1 و2)
- **الهوية**: `profiles` (اسم ونبذة) منفصل عن `profile_details` (جنس، سنة الميلاد فقط، مدينة) لتقليل كشف البيانات.
- **المؤسسات**: `organizations` ← `centers` (يمكن أن يكون المركز مستقلًا) + جداول عضوية لكل منهما. التوثيق (`status`) لا يغيّره إلا مدير المنصة.
- **ولي الأمر**: `parent_student_links` تُنشأ فقط عبر رمز لمرة واحدة يولّده الطالب (`parent_link_codes`، يُخزن مُجزّأً hash، صالح 48 ساعة، مع حد للمحاولات).
- **الحلقات**: `halaqat` (حيث `center_id = NULL` تعني حلقة مستقلة دون مركز وهمي)، `halaqa_memberships` (طلبات وعضويات)، `quran_sessions`، `attendance_records`.
- **التسميع**: `quran_progress_records` مع خمس إشارات منفصلة: المقدار (`ayah_count` محسوب من مرجع السور)، الإتقان، جودة التلاوة، الالتزام بالخطة، والحضور (جدول مستقل). `quran_error_records` للأخطاء، و`quran_assignments` للواجب القادم.
- **المرجع**: `quran_surahs` (114 سورة، 6236 آية، رواية حفص).
- **التشغيل**: `notifications`، `audit_logs` (إضافة فقط)، `privacy_requests`، `private.rate_limits`.

## قواعد السجلات المعتمدة
- يرى الطالب ووليّ الأمر السجلات **المعتمدة فقط**.
- لا يملك الطالب أي صلاحية تعديل.
- تعديل سجل معتمد يتم فقط عبر `amend_progress_record` مع سبب إلزامي؛ يُرفع رقم المراجعة ويُحفظ الفرق (قبل/بعد) في سجل التدقيق.
- لا يمكن حذف سجل معتمد حتى من مالك الجدول (trigger).

## قرارات وافتراضات موثّقة
- **Cache Components معطّل**: كل الصفحات تقريبًا خاصة بالمستخدم ومحمية بـ RLS؛ العرض الديناميكي التقليدي أبسط وأأمن.
- **مكتبة المكونات**: مكونات خفيفة خاصة مبنية بـ Tailwind بدل مكتبة كبيرة، لتقليل حجم التحميل على الاتصالات الضعيفة. كلها تعمل بالاتجاه من اليمين لليسار.
- **الانضمام بالدعوة فقط** معطّل حتى تُنفّذ الدعوات في المرحلة الثالثة، كي لا تُنشأ حلقة لا يمكن الانضمام إليها.
- **روابط الاجتماعات** تُحفظ على الجلسة ولا يراها إلا أعضاء الحلقة وأولياء أمورهم.
- **موقع الحلقة** نصي عام (مدينة أو حي)، والواجهة تنبّه بعدم كتابة عناوين سكن.
- **إدارة المنصة لا ترى سجلات تسميع الأطفال** افتراضيًا؛ ترى الحسابات والأدوار والتدقيق فقط.
- **المحفّظ** يرى ملخص الطالب داخل حلقته فقط، لا مجموعه من حلقات محفّظين آخرين.
- **الشعار**: الملف الأصلي محفوظ دون تعديل في `public/brand/halaqati-logo-original.png`، والنسخ المصغّرة مأخوذة منه بتصغير نسبي واقتصاص الهامش الفارغ فقط.
