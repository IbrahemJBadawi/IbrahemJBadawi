# منصة الجمال | Al Jamal

متجر إلكتروني فلسطيني للملابس اليومية الأساسية بنموذج **البيع حسب الطلب عبر موردين محليين**، دون مخزون ودون رأس مال تشغيلي مسبق:

1. العميل يرسل طلبه **دون دفع**.
2. المدير يؤكد مع المورد التوفر والمقاس واللون والسعر وتكلفة التوصيل.
3. المدير يعتمد السعر النهائي، فتظهر للعميل تعليمات **التحويل البنكي** في صفحة طلبه.
4. العميل يحوّل ويرفع إثبات التحويل. **رفع الإثبات لا يعني الدفع.**
5. المدير يتحقق يدويًا من وصول المبلغ إلى الحساب ثم يؤكد الدفع.
6. المدير يحوّل مستحقات المورد **خارج المنصة**، والمنصة توثّق التحويل فقط.
7. المورد يجهز ويشحن مباشرة إلى العميل، والمدير يسجل شركة التوصيل ورقم التتبع.
8. المدير يؤكد التسليم صراحةً، والنظام يحسب الربح الفعلي.

لا يوجد ربط مصرفي، ولا بوابة دفع، ولا تكامل آلي مع الموردين أو شركات التوصيل، ولا أي تحويل مالي تلقائي.

**مزايا مأخوذة من نموذج TechMood ومكيّفة للمتجر:** إشعارات داخل الموقع (وبريد اختياري)، تذاكر دعم مع ملاحظات داخلية، فواتير تصدر تلقائيًا بعد تأكيد الدفع، مساعد تسوق ذكي على Gemini (اختياري، ومخفي بدون مفتاح)، وتثبيت المتجر كتطبيق على الهاتف (PWA).

**التقنيات:** Next.js 16، TypeScript، Tailwind CSS 4، وPostgreSQL مع سياسات RLS متوافقة مع Supabase (PGlite محليًا). المصادقة محلية أو عبر Supabase Auth.

## التشغيل محليًا

```bash
cd jamal-platform
npm install
npm run setup        # ينشئ .env.local مع AUTH_SECRET عشوائي
npm run db:migrate   # قاعدة PGlite في .data/pglite + كل الـ migrations
npm run seed:demo    # (اختياري) منتجات ومورد ومناطق تجريبية بالشيكل
npm run dev          # http://localhost:3000
```

**أول مسؤول:** سجّل من `/register`، ثم **أوقف** `npm run dev` (قاعدة PGlite تُفتح من عملية واحدة فقط) وشغّل `npm run admin:grant -- your@email.com`، ثم أعد التشغيل وافتح `/admin`. مع Postgres خارجي (`DATABASE_URL`) لا حاجة لإيقاف الخادم.

**البيانات التجريبية:**
- كل منتج تجريبي يحمل شارة «منتج تجريبي».
- الطلبات عليها تُسجّل كطلبات اختبار وتُستثنى من المبيعات والأرباح.
- تعليمات الدفع التجريبية تقول صراحةً «لا تحوّل أي مبلغ».
- للحذف الكامل قبل الإطلاق: `npm run seed:demo -- --remove`.

## ما يجب أن تُدخله بنفسك قبل الإطلاق (من لوحة الإدارة)

1. **الإعدادات ← إعدادات التحويل البنكي:** اسم المستفيد، البنك (مثل بنك فلسطين)، وتفاصيل التحويل التي توافق على نشرها (رقم الحساب أو IBAN). وأيضًا التعليمات، وصلاحية التعليمات بالساعات، وسياسة مراجعة الإثباتات، ووسيلة التواصل. **الحقول فارغة عمدًا**، ولم يُخترع أي رقم حساب.
2. **الدول والشحن:** أضف فقط المحافظات التي تأكدت من التوصيل إليها، مع رسوم التوصيل على العميل وتكلفتها المتوقعة عليك ومدتها. المحافظات الفلسطينية الـ16 موجودة كقائمة مرجعية بلا أسعار.
3. **الموردون:**
   - سجّل كل مورد وشروطه: قطعة واحدة، شحن مباشر، دفع بعد التحصيل، جهة التحصيل، وطريقة التسوية.
   - اعتماد المورد يتطلب أن تؤكد بنفسك موافقته الفعلية على الشروط، ويُسجّل ذلك باسمك ووقته.
4. **المنتجات:** اربط كل منتج بمورد أساسي **معتمد** قبل النشر، فقاعدة البيانات ترفض نشر غير ذلك. أكّد التوفر والسعر دوريًا.
5. **الصفحات والسياسات:** راجع نصوص الإرجاع والخصوصية والشروط قانونيًا ووفق اتفاقات الموردين.
6. **الإعدادات العامة:** بيانات التواصل وواتساب.
7. **الفواتير:** الاسم القانوني والرقم الضريبي ونص التذييل. بدون رقم ضريبي تُكتب الفاتورة «فاتورة مبيعات — ليست فاتورة ضريبية». راجع متطلبات الفوترة مع محاسب.
8. **مساعد التسوق الذكي:** معطّل افتراضيًا. فعّله من الإعدادات فقط بعد إضافة `ANTHROPIC_API_KEY` (انظر أدناه).

## مزايا TechMood المضافة

| الميزة | أين | ملاحظات |
|---|---|---|
| الإشعارات | الجرس في الأعلى، `/account/notifications`، `/admin/notifications` | تُنشئها قاعدة البيانات عبر triggers (تغيّر حالة الطلب، الإثباتات، الإلغاء، الإرجاع، ردود الدعم، الفواتير). العميل يختار ما يصله، وتحديثات الطلب إلزامية. |
| البريد الإلكتروني | `POST/GET /api/email/dispatch` | الرسائل تنتظر في `email_outbox`، ولا يُرسل شيء إلا بعد ضبط `RESEND_API_KEY` و`EMAIL_FROM` و`CRON_SECRET`. خطة Resend المجانية حوالي 3000 رسالة شهريًا (تأكد من الأسعار الحالية). |
| تذاكر الدعم | `/support`، `/admin/tickets` | الزائر يحصل على رابط خاص للتذكرة. الملاحظات الداخلية لا يراها العميل (RLS). |
| الفواتير | رابط «عرض الفاتورة» في صفحة الطلب، `/admin/invoices` | تصدر تلقائيًا مرة واحدة عند تأكيد الدفع، برقم `INV-السنة-000001`. عند الاسترداد تُعلَّم ولا تُحذف ولا تُعدّل. تُطبع من المتصفح (حفظ كـ PDF). |
| حسابات الاسترداد | صفحة الطلب ← لوحة الطلب | العميل يكتب أين يريد استلام المبلغ، والمدير وحده يراه. لا تحويل آلي. |
| مساعد التسوق الذكي | `/assistant` | يبحث في المنتجات المنشورة فقط بأسعار البيع (لا يرى التكلفة أو المورد)، ويجيب عن التوصيل. لا يعدّل طلبات ولا يؤكد دفعًا. |
| التثبيت كتطبيق | `/app`، ولافتة التثبيت | Manifest وService Worker لصفحة «غير متصل» فقط، ولا تُخزّن الصفحات الخاصة. |

### المساعد الذكي: الإعداد
- يعمل على **Google Gemini** (النموذج `gemini-2.5-flash`، ويمكن تغييره بالمتغير `GEMINI_MODEL`). مفتاح Gemini من Google AI Studio له خطة مجانية بحدود يومية تحددها Google.
- **مخفي تمامًا** (لا رابط ولا صفحة) ما لم يُضبط `GEMINI_API_KEY` في إعدادات الخادم. ويمكن للمدير إيقافه من الإعدادات.
- انتبه: في الخطة المجانية قد تستخدم Google المحادثات لتحسين خدماتها. لا يُرسل للمساعد إلا سؤال العميل وبيانات الكتالوج العامة.
- الحد اليومي: `AI_DAILY_LIMIT_USER` (افتراضيًا 30 رسالة) و`AI_DAILY_LIMIT_GUEST` (10 رسائل، حسب IP مُشفّر بـ hash ولا يُحفظ الـ IP نفسه)، إضافة إلى 8 رسائل في الدقيقة.
- محادثات المسجّلين تُحفظ في حسابهم. محادثات الزوار تبقى في المتصفح فقط.

## البنية والجداول

```
supabase/migrations/
  …0001_core_schema.sql         المخطط الأساسي
  …0002_rls_policies.sql        الصلاحيات (RLS)
  …0003_reference_data.sql      الفئات والعملات والصفحات
  …0004_palestine_workflow.sql  نموذج فلسطين (إضافي وغير تدميري)
src/lib/orders/states.ts        قواعد الحالات والانتقالات (مختبرة)
src/lib/orders/workflow.ts      كل عمليات دورة الطلب داخل معاملات قاعدة بيانات
src/lib/orders/core.ts          إنشاء الطلب وحساب السعر على الخادم ومنع التكرار
src/lib/finance.ts              الإيرادات والتكاليف والأرباح (مختبرة)
src/app/(store)/order/[number]  صفحة الطلب الخاصة للعميل (الدفع، الإثبات، الإلغاء، الإرجاع)
src/app/admin/…                 لوحة الإدارة (الطلبات، المستحقات، الموردون…)
```

**جداول جديدة:**

| الجدول | الوظيفة |
|---|---|
| `governorates` | المحافظات |
| `payment_settings` | بيانات التحويل البنكي، للمدير فقط |
| `payment_proofs` | إثباتات التحويل وقرار المراجعة |
| `payment_proof_files` | ملفات الإثبات، للمدير فقط ومحمية بـ RLS |
| `order_expenses` | رسوم الدفع والتحويل، وتكلفة الإرجاع، ومصروفات أخرى |
| `refunds` | الاستردادات: معلّق ثم منفّذ ثم ملغى |

**أعمدة جديدة على جداول موجودة:**
- `orders`: الحالات الجديدة، والسعر المعتمد ومَن اعتمده، وصلاحية الدفع، والمبلغ المحصّل والتحقق منه ومرجعه، والمحافظة، و`idempotency_key` لمنع التكرار، ورابط الطلب الخاص، وبيانات الإلغاء (السبب، المسؤول عن التكلفة، المبلغ غير القابل للاسترداد).
- `order_items`: تأكيد التوفر لكل سطر، ومَن أكده ومتى.
- `fulfillment_records`، وهو سجل لكل مورد في كل طلب، صار يضم الشحنة **والتسوية معًا**:
  - حالة التسوية، والمبلغ المحوّل وتاريخه ومرجعه ومَن سجله.
  - التكاليف الفعلية، ولمن تُدفع تكلفة التوصيل.
  - سبب فشل التسليم، والمبلغ الذي يعيده المورد.
- `suppliers`: حالة الاتفاق (قيد التواصل، قيد التفاوض، معتمد، موقوف) وكل شروطه وتواريخ التأكيد.
- `products`: تاريخ آخر تأكيد للتوفر والسعر، ومدة التجهيز.
- `shipping_zones`: المحافظة، والتكلفة المتوقعة، وشركة التوصيل.

## قواعد مهمة مطبّقة على الخادم وقاعدة البيانات

- العميل لا يستطيع تغيير حالة الدفع أو الطلب أو الأسعار، لا من الواجهة ولا من قاعدة البيانات (RLS).
- اعتماد السعر يتطلب تأكيد توفر كل المنتجات. والإرسال للمورد أو التجهيز أو الشحن يتطلب **دفعًا مؤكدًا وتوفرًا مؤكدًا**.
- قبول الإثبات يتطلب المبلغ الواصل فعليًا وتاريخ التحقق، وإقرار المدير بأنه تحقق بنفسه. المبلغ الناقص يُسجّل ويبقى الطلب بانتظار الباقي.
- تسجيل تسوية المورد «تم التحويل» يتطلب المبلغ والتاريخ والمرجع، ولا يُسمح به قبل تحصيل المبلغ من العميل.
- رقم التتبع لا يعني التسليم، والتسليم تأكيد صريح من المدير.
- الإلغاء بعد الدفع يُنشئ استردادًا **معلّقًا** حتى تسجيل تنفيذه بمرجع وتاريخ. وإذا كان المورد قد قبض، يُسجّل ما يجب أن يعيده كمعلّق أيضًا.
- كل انتقال حالة يُسجّل مع الحالة السابقة ومَن نفّذه ومتى. والعمليات المالية تُسجّل في سجل العمليات غير القابل للتعديل.
- إرسال الطلب مرتين بالخطأ ينتج طلبًا واحدًا. وأي فشل أثناء الحفظ لا يترك طلبًا ناقصًا، لأن العملية كلها معاملة واحدة.
- إيقاف مورد يُخفي منتجاته تلقائيًا.
- **الربح الفعلي** = صافي المحصّل − تكلفة المنتجات − تكلفة التوصيل الفعلية (مرة واحدة، أيًّا كان المستلم) − رسوم الدفع والتحويل والمصروفات وتكاليف الإرجاع + ما أعاده المورد فعليًا. الأموال المحوّلة للمورد ليست ربحًا، ولا تُحوَّل العملات.

## النشر (Supabase + Vercel)

### نسخة العرض على Vercel (بدون قاعدة بيانات)
إذا نُشر المشروع على Vercel **بدون** `DATABASE_URL`، يعمل تلقائيًا كنسخة عرض:
- قاعدة بيانات داخل الذاكرة تُبنى عند تشغيل الخادم، فيها الكتالوج التجريبي ومناطق توصيل تجريبية.
- **لا شيء يُحفظ**، والبيانات تُمسح عند إعادة تشغيل الخادم، ولافتة أعلى الموقع توضح ذلك.
- **بيانات بنكية حقيقية لا تظهر أبدًا في نسخة العرض.**
- للدخول إلى لوحة الإدارة في نسخة العرض أضف في Vercel `DEMO_ADMIN_PASSWORD` (10 أحرف أو أكثر)، ثم سجّل الدخول بـ `admin@jamal.demo`. طلبات العرض تظهر في الإدارة عند تفعيل «طلبات الاختبار».
- يُفضّل إضافة `AUTH_SECRET` (32 حرفًا عشوائيًا)، وإلا قد تُسجَّل خارج الحساب عند إعادة تشغيل الخادم.
- إعدادات مشروع Vercel: Root Directory = `jamal-platform`. وVercel يبني فرع الإنتاج (`main` عادة)، فيجب دمج هذا الفرع فيه.

### النسخة الحقيقية
**الوضع الحالي:** إنشاء مشروع Supabase جديد مرفوض لأن حسابك وصل حد المشروعين المجانيين النشطين.

**بيانات التحويل البنكي من البيئة (اختياري):** `BANK_BENEFICIARY_NAME` و`BANK_NAME` و`BANK_TRANSFER_DETAILS` و`BANK_INSTRUCTIONS`. تُكتب مرة واحدة عند أول تشغيل إذا كانت إعدادات الدفع فارغة، ثم تُعدّل من لوحة الإدارة.

**الخطوات عندما تكون جاهزًا:**

1. **Supabase:** أوقف مؤقتًا (Pause) أو احذف مشروعًا مجانيًا غير مستخدم، أو رقِّ الخطة. ثم أنشئ مشروعًا جديدًا في منطقة `eu-central-1`.
2. طبّق الـ migrations الستة بالترتيب، عبر `supabase db push` أو بنسخها إلى SQL Editor. **لا تطبّق** `db/local/auth_shim.sql`.
3. **Vercel:**
   - استورد المستودع، واجعل Root Directory = `jamal-platform`.
   - أضف المتغيرات: `NEXT_PUBLIC_SITE_URL`، و`DATABASE_URL` (Transaction pooler، المنفذ 6543، سري)، و`AUTH_PROVIDER=supabase`، و`NEXT_PUBLIC_SUPABASE_URL`، و`NEXT_PUBLIC_SUPABASE_ANON_KEY`.
   - وإذا أردت رفع صور المنتجات: `SUPABASE_SERVICE_ROLE_KEY` (سري جدًا).
   - اختياري: `GEMINI_API_KEY` للمساعد، و`RESEND_API_KEY` و`EMAIL_FROM` و`CRON_SECRET` للبريد. Vercel Cron في الخطة المجانية يعمل مرة يوميًا فقط، فاستخدم خدمة cron خارجية مجانية إن أردت إرسالًا أسرع.
4. **حد حجم الطلب:** Vercel يرفض الطلبات الأكبر من 4.5MB، لذلك حد رفع الملفات في المنصة 4MB.
5. **الإثباتات:** تُخزّن داخل قاعدة البيانات (جدول محمي)، فلا تحتاج حاوية تخزين.
6. **الخطط المجانية:** خطة Vercel المجانية مخصّصة للاستخدام غير التجاري، والاستخدام التجاري يتطلب خطة Pro (نحو 20$ شهريًا). مشاريع Supabase المجانية تتوقف بعد أسبوع من عدم النشاط.

## ما لم يُنجز أو يمنع الإطلاق الحقيقي

- **بيانات التحويل البنكي ومناطق التوصيل الحقيقية والموردون الحقيقيون** لم تُدخل بعد، فلا يمكن استقبال طلبات حقيقية قبل إدخالها.
- **النشر** لم يتم (الأسباب أعلاه).
- **الإشعارات** داخل الموقع تعمل. البريد جاهز لكنه لا يُرسل قبل ضبط Resend. **واتساب وSMS غير موجودين**، والتواصل مع المورد يدوي.
- **المساعد الذكي (Gemini)** لم يُختبر مع مفتاح حقيقي (لا يوجد مفتاح في بيئة التطوير). جرى التحقق فقط من أنه مخفي بدون مفتاح.
- **استعادة كلمة المرور** في الوضع المحلي غير موجودة.
- **حماية التكرار المفرط** (rate limit) داخل ذاكرة الخادم فقط.
- **الواجهة الإنجليزية** غير مبنية، والبنية جاهزة لها.
- **نصوص السياسات** مبدئية وتحتاج مراجعة قانونية.
- بعد الإرجاع يحدد المدير حالة الطلب يدويًا: إما «بانتظار الاسترداد» أو الاستبدال.
